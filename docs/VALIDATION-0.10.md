# MyTube 0.10.0 validation

## Behavior and ownership

Sidebar focus paints before destination construction (two frame callbacks, without a data wait). Rapid remote repeats cancel the pending destination selection. Enter is still optional. Every browse route owns a data snapshot and an independent ViewModel job; a result completing after navigation updates its captured route rather than the current route. Home pagination continues while another page is visible. Library operations and extraction run off the UI thread; Home preparation already uses a worker dispatcher.

Visited Home, Search, Subscriptions, Library, Live, Channel, Settings and Interests compositions remain in memory for the current activity. Only the active slot is measured/placed. Inactive semantics are cleared and focus entry is canceled; content-owned transitions transfer focus to the destination, while sidebar focus remains in the sidebar. Header/video focus requesters and grid scroll state belong to individual routes. There are eight route slots, including one reusable channel slot. This does not persist layouts across activity/process destruction or promise that data updates never recompose components.

Home retains its committed feed and page count; Library reloads local history on entry; Live rechecks after one minute or a preference invalidation, replacing the previous discovery results; opening a channel loads that channel. Subscription/interest/progress updates reach retained snapshots. Preference edits/history clearing invalidate Home/Live results for a subsequent visit, including edits made during an outstanding load. Search retains its query, keyboard mode and results. Its recommendations can update when an initial Home load finishes in the background. Existing rows remain usable during loading.

Related-video Up handling belongs to the grid. Up from a later row uses normal focus movement; only Up above row zero returns to the player controls. The root player no longer intercepts all related-grid Up events. Empty related lists still support Up to controls; Up next cancellation remains separate.

## Chapter timeline

NewPipeExtractor v0.26.5's StreamInfo stream segments supply original chapter titles and start times. The gateway converts seconds to milliseconds and normalizes negative/duplicate/out-of-order starts once into video-owned immutable metadata. The renderer derives ends from the actual current playback duration, preserves an unlabeled prefix if needed and ignores out-of-duration divisions. Unknown durations and live streams do not receive invented chapters. Metadata is cleared on each video load, including retries/switches.

The bottom progress bar draws separated sections, red played portions, a gray remaining track and a focused white thumb. The current chapter title appears beside the channel and follows playback/ten-second remote seeking across boundaries. The whole timeline remains one focus stop, preserving existing Up/Down/play/pause routing. Missing chapter data produces one continuous track.

The on-device public fixture `https://www.youtube.com/watch?v=rfscVS0vtbw` supplied **35 chapters**, starting with Introduction (0 ms) and Installing Python & PyCharm (105,000 ms). The real-player check observed playback, paused, sought across that boundary in both directions, checked the title and hid/reopened the controls. Extracted metadata and a screenshot are retained in `artifacts/validation/0.10/extracted-chapters.json` and `artifacts/screenshots/0.10-debug/segmented-progress.png`. Native video surfaces may appear black in screenshots; playback was independently observed through Media3.

## Paired completed workload

The same standalone Home/Search instrumentation workload was run against 0.9.0 debug and final 0.10.0 debug. First Search/Home took 7,567 → 6,627 ms elapsed and 7,982 → 7,056 ms app CPU. Six warm trips took 26,384 → 11,744 ms elapsed (55.5% less) and 27,078 → 11,237 ms app CPU (58.5% less). Warm app-process VmHWM was 267,340 → 264,280 KiB; retained VmRSS was 246,932 → 263,956 KiB. This is one paired instrumented run with idle/semantics waits, not a release frame-rate or statistical claim. The first sample is first Search construction after loaded Home, not cold process startup. Process-family memory, agent-token cost and peak memory after visiting every route were not measured. Raw reports, workload/APK hashes and bounds are in `artifacts/performance/retained-pages/`.
